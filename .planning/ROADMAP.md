# Roadmap: MLX

## Overview

MLX — the personal coding dataset and model pipeline progresses through eight contract-mandated acceptance boundaries: safe identity and brownfield migration control; durable local foundations; authorized repository facts; immutable evidence and preference claims; a Hugging Face-native dataset release; executable PersonalBench evaluation; real Apple Silicon training evidence; and an honest local Studio with end-to-end acceptance. The event success floor is tracked as separate evidence inside the relevant phases and never substitutes for phase or project completion.

## Phases

**Phase Numbering:**

- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions marked as `INSERTED`

- [x] **Phase 1: Identity, cleanup, baseline, and migration map** - Establish collision-safe MLX identity, stable validation, and proven ownership for every brownfield component. (completed 2026-07-16)
- [ ] **Phase 2: Foundation: configuration, SQLite, CAS, runs, and job queue** - Establish contained, durable, immutable, and recoverable local operations.
- [ ] **Phase 3: GitHub inventory, mirrors, identities, and accurate metrics** - Turn explicitly selected repositories into pinned snapshots and defensible engineering metrics.
- [ ] **Phase 4: Evidence extraction, accepted-state quality, and preference profile** - Produce immutable accepted-state evidence and challengeable, scoped coding preferences.
- [ ] **Phase 5: Hugging Face dataset compiler, deduplication, and leakage-safe splits** - Release reproducible Hugging Face-native datasets and derived training views that pass privacy and leakage gates.
- [ ] **Phase 6: Runtime tools, worktrees, MLX PersonalBench, and model adapters** - Execute isolated repository tasks and compare model variants with paired, task-level evidence.
- [ ] **Phase 7: Apple Silicon MLX-LM training, experiment tracking, and paired evaluation** - Prove real E2B/E4B training and inference on the target Mac with reproducible experiment lineage.
- [ ] **Phase 8: Studio, presentation mode, privacy review, and end-to-end acceptance** - Expose validated artifacts through an honest local Studio and close the complete acceptance contract.

### Phase 2: Foundation: configuration, SQLite, CAS, runs, and job queue

**Goal:** Every later MLX workflow runs on contained configuration, migrated state, immutable artifacts, and recoverable orchestration.
**Mode:** mvp
**Depends on:** Phase 1
**Requirements:** FNDN-01, FNDN-02, FNDN-03, FNDN-04, FNDN-05, FNDN-06, FNDN-07, FNDN-08, FNDN-09, FNDN-10, FNDN-11, FNDN-12
**Success Criteria** (what must be TRUE):

1. Invalid configuration fails with actionable diagnostics, while every mutable or extracted path remains beneath `MLX_HOME` and traversal, symlink, and archive escapes fail closed.
2. A fresh or supported prior catalog opens through persisted migrations with foreign keys and WAL enabled; `mlx doctor` reports SQLite capability and enforces the catalog-owner gate when required.
3. Immutable source, patch, trace, report, and generated bytes round-trip through atomic SHA-256 storage with integrity verification and durable catalog or analytical references.
4. Every run has an immutable, checksummed lineage manifest, and repeating a deterministic stage with identical valid inputs reuses its committed output.
5. Operator can inspect, cancel, crash, recover, and resume durable leased work without duplicate outputs or orphan child processes, then apply retention or garbage collection without deleting referenced artifacts.

### Phase 3: GitHub inventory, mirrors, identities, and accurate metrics

**Goal:** Operators can turn only explicitly authorized GitHub repositories into immutable snapshots and reproducible, correctly labeled engineering facts.
**Mode:** mvp
**Depends on:** Phase 2
**Requirements:** REPO-01, REPO-02, REPO-03, REPO-04, REPO-05, REPO-06, REPO-07, REPO-08, REPO-09, REPO-10, REPO-11, REPO-12, REPO-13, REPO-14, REPO-15, REPO-16, REPO-17, REPO-18
**Success Criteria** (what must be TRUE):

1. Operator can inspect token-safe authentication and complete paginated repository discovery, while every repository stays pending until explicit inclusion and export policies are assigned and access alone triggers no cloning or downstream use.
2. Selected repositories update as resumable bare mirrors, recover after interruption, pin immutable snapshots, and never write source content into the application checkout.
3. Operator can normalize aliases, noreply addresses, mailmaps, and co-authors without guessed identity matches and can see measured identity coverage plus unmatched contributors.
4. Repository, Git-history, current-code, ownership, collaboration, engineering-pattern, and language-evolution metrics reconcile to documented deterministic definitions and display population, exclusions, timestamp, snapshot, source classification, and `LIVE`, `REPLAY`, or `FIXTURE`.
5. Synthetic repository oracles reproduce expected results for merges, reverts, renames, aliases, binaries, generated files, tests, and temporal history, including binary arithmetic exclusions and the “surviving attributed lines” label.

### Phase 4: Evidence extraction, accepted-state quality, and preference profile

**Goal:** Authorized repository snapshots yield immutable, provenance-complete evidence and defensible coding-preference artifacts.
**Mode:** mvp
**Depends on:** Phase 3
**Requirements:** EVID-01, EVID-02, EVID-03, EVID-04, EVID-05, EVID-06, EVID-07, EVID-08, EVID-09, EVID-10, EVID-11, EVID-12, EVID-13, EVID-14, EVID-15
**Success Criteria** (what must be TRUE):

1. Every evidence record traces through stable schema, snapshot, source, SHA, path, object, validation, privacy, generator, and task-group identifiers, with raw bytes in CAS and reproducible extraction for identical inputs.
2. Operator can inspect separate accepted-state, survival, verification, semantic, instruction, context, uniqueness, recency, repository, and privacy components plus an interpretable Q0-Q4 tier whose hard gates override weighted scores.
3. Human and AI-assisted accepted code follow the same default quality policy, while semantic workers emit immutable schema-validated sidecars with bounded attempts and model/prompt lineage and retain no hidden chain-of-thought.
4. Every preference is correctly scoped to global, language, framework, or repository context and exposes support, independent repositories, uncertainty, counter-evidence, exceptions, and training implications without promoting local configuration into a global rule.
5. Each profile snapshot emits both `developer_profile.json` and `DEVELOPER_PROFILE.md`, and the prompting/training profile excludes whole-repository, temporal, and future holdout evidence.

### Phase 5: Hugging Face dataset compiler, deduplication, and leakage-safe splits

**Goal:** Operators can build immutable, privacy-checked Hugging Face releases whose schemas, provenance, splits, and derived exports are reproducible and leakage-safe.
**Mode:** mvp
**Depends on:** Phase 4
**Requirements:** DATA-01, DATA-02, DATA-03, DATA-04, DATA-05, DATA-06, DATA-07, DATA-08, DATA-09, DATA-10, DATA-11, DATA-12, DATA-13, DATA-14, DATA-15, DATA-16, DATA-17, DATA-18, DATA-19, DATA-20, DATA-21, DATA-22, DATA-23, DATA-24
**Success Criteria** (what must be TRUE):

1. Canonical examples cover all six required task families using grounded pre-change prompts and bounded, recorded context selection that does not expose target patches or future state.
2. A fingerprinted Parquet/Arrow release exposes explicit Hugging Face features for all eight required configs, loads every config and split through `datasets.load_dataset` without custom code, and includes complete card, schema, manifest, checksum, statistics, report, Croissant, limitation, and visible Viewer-validation artifacts.
3. Repository, temporal, future, and `task_group_id` assignments are deterministic before variants expand; siblings never cross splits, holdout evidence never reaches training preferences, and any critical leakage finding blocks release.
4. Filtering and exact/near deduplication preserve recorded reasons, clusters, representatives, thresholds, and cross-split reports, while secret, PII, visibility, rights, license, and export-policy gates block unsafe egress.
5. Validated canonical rows deterministically produce parseable MLX-LM, TRL, and LightEval exports, including next-assistant-action trajectory supervision, token/truncation/template statistics, immutable source fingerprints, and explicit publication preview and confirmation.

**Event success floor evidence (tracked separately; does not complete this phase or project):**

- A local/private release contains 500-2,000 validated Hugging Face-ready examples and loads through `datasets`; this presentation-sized release is not evidence of the 25,000-50,000 core target.

### Phase 6: Runtime tools, worktrees, MLX PersonalBench, and model adapters

**Goal:** Operators can execute isolated coding tasks and compare model behavior under identical policies with sample-level, statistically defensible results.
**Mode:** mvp
**Depends on:** Phase 5
**Requirements:** BNCH-01, BNCH-02, BNCH-03, BNCH-04, BNCH-05, BNCH-06, BNCH-07, BNCH-08, BNCH-09, BNCH-10, BNCH-11, BNCH-12, BNCH-13, BNCH-14, BNCH-15, BNCH-16
**Success Criteria** (what must be TRUE):

1. Models can use only the nine fixed, schema-validated host tools with bounded/paginated output, contained paths, observable traces, and inspected `check_id` values rather than arbitrary shell.
2. Every execution begins from the recorded `base_sha` in a disposable worktree and leaves neither source-checkout mutations, worktrees, nor process groups behind after pass, failure, timeout, cancellation, or crash.
3. RepoTaskBench, NavBench, StyleBench, GeneralizationBench, TemporalBench, and FutureBench execute their defined task populations and report their task-level execution, localization, preference, isolation, safety, efficiency, and error outcomes.
4. Base, profile-prompted, and available tuned variants run identical tasks, tools, budgets, checks, sampling, and hardware policy; private tasks cannot reach cloud models without sanitization, approved egress policy, and confirmation.
5. Publishable results include paired deltas, bootstrap intervals, McNemar and Bradley-Terry analyses, effect sizes, task counts, missing/error categories, contamination audit, and Parquet/Hugging Face sample artifacts with compatible LightEval metrics.

**Event success floor evidence (tracked separately; does not complete this phase or project):**

### Phase 7: Apple Silicon MLX-LM training, experiment tracking, and paired evaluation

**Goal:** Operators have real target-machine evidence for reproducible E2B/E4B MLX-LM experiments and can separate profile prompting gains from tuning gains.
**Mode:** mvp
**Depends on:** Phase 6
**Requirements:** TRNG-01, TRNG-02, TRNG-03, TRNG-04, TRNG-05, TRNG-06, TRNG-07, TRNG-08, TRNG-09, TRNG-10
**Success Criteria** (what must be TRUE):

1. Preflight records the installed MLX-LM interface, immutable model revision, tokenizer, chat template, tool format, disk, memory, and software/hardware versions before an experiment starts.
2. The target Mac proves E2B load, generation, and structured tool use, and uses E2B for bounded smoke, tool-format, and data-scaling experiments before principal E4B work.
3. E4B safe, balanced, and aggressive profiles enforce measured memory limits and consume only validated, fingerprinted exports while recording exact configurations, commands, seeds, metrics, checkpoints, and source release.
4. Operator can stop and resume checkpointed training with lineage intact, then load the resulting adapter for inference and execute a paired benchmark subset on the target Apple Silicon machine.
5. Experiment manifests, model cards, and paired reports connect every dataset, profile, benchmark, model, adapter, version, resource measurement, result, and limitation while distinguishing profile, tuning, and combined gains and never counting mocks or capability skips as hardware acceptance.

**Event success floor evidence (tracked separately; does not complete this phase or project):**
