**As an** operator or maintainer, **I want to** use one collision-safe MLX product surface and inspect an honest validation baseline plus complete replacement map, **so that** I can operate and evolve the brownfield system without ambiguous identity, unsafe takeover, or false acceptance.

<objective>
Make the walking CLI skeleton an installable, uniquely owned `mlx` executable and eliminate legacy user-facing product identity from source and generated package/help artifacts.

Purpose: Operators must know which MLX they are invoking before doctor can classify PATH candidates, while maintainers need a repeatable audit rather than a one-time rename.
Output: Canonical package metadata, packaged ownership marker, isolated bin proof, identity scanner, and corrected legacy UI copy without restoring legacy behavior to the public entry.
</objective>

## Scope Justification

This plan owns 10 paths because the sole-bin package artifact and retained-surface identity audit are one acceptance boundary: the isolated packed help/marker output is itself an input to the identity audit, while the four retained source paths are direct copy repairs rather than a second subsystem. The three tasks keep package configuration, audit implementation, and retained copy separated, introduce no dependency change, and preserve the Plan 01 entry unchanged.

## Trust Boundaries

| Boundary | Description |
|---|---|
| Package metadata → installed executable | An installed artifact claims ownership of the shared `mlx` name. |
| Repository/artifact paths → identity scanner | Scanner inputs can point toward private, ignored, or operator-controlled data. |
| Product copy → operator trust | Ambiguous wording can spoof affiliation with Apple's project or legacy behavior. |
